# ADR-072 — Clôture du jalon M3 avec réserves, passage à M4

- **Date** : 2026-11-05
- **Statut** : accepté (décision de Killian)
- **Jalons** : M3 (Décision), M4 (Exécution sûre)
- **Exigences** : PARTIE 29 (Definition of Done), PARTIE 30 (jalons), contrat agent 1.4 ;
  ADR-042 et ADR-065 (même démarche pour M1 et M2)
- **Demande** : Killian, 2026-11-05, « ok tu peux clore alors »

## Contexte

La DoD de M3 compte 29 tests : T-200..T-205, T-220..T-223, T-230..T-232, T-240..T-245,
T-380..T-384, T-390..T-392, T-460..T-461. La sortie attendue par la PARTIE 30 est « premiers
gains réels par batching, `/rfx why` complet ». Le premier gain a été reporté à M4 par
Killian le 2026-11-05 (ADR-069, option A) : il n'est pas faisable sûrement en M3.

## Décision

**M3 est clos avec réserves.** Comme pour M1 et M2, c'est une divergence volontaire à
l'ordre des jalons, décidée par Killian.

**Acquis**, dont M4 a besoin :

- risque de chaque unité, règles R1..R10 cumulées, blast radius (C-14 ; ADR-066) ;
- compatibilité : six verdicts, priorité des sources, `[overrides]`, propriétés détectées
  (réflexion, transformateur concurrent), aucun nom de mod dans le moteur (C-33 ;
  ADR-067) ;
- décision : filtre dur avec motifs DM-15, gain = temps économisé, aucune activation sans
  mesure (R-410), politique des modes, plafond TL2, tenue de 600 ticks et verrouillage
  pour oscillation (C-15 ; ADR-068) ;
- chaîne causale de chaque décision, 37 codes stables traduits, `/rfx why` complet
  (C-43 ; ADR-070) ;
- chaîne de mesure d'un gain, étalonnée en A/A sur données simulées, branchée sur les
  relevés du jeu (ADR-069) ;
- flux de données : zéro sous-approximation et 63,3 % `EXACT` sur le corpus annoté de 150
  méthodes (C-11, T-204 ; ADR-071) ; déterminisme statique (C-13 ; ADR-058) ;
- persistance des descripteurs d'une partie à l'autre, invalidée par l'empreinte et par
  le code d'analyse (C-32, `workload_cache` ; ADR-064).

**Réserves**, reprises dans `tasks/todo.md` :

| test ou sortie | ce qui manque | où il se fera |
|---|---|---|
| premier gain par batching | aucun gain sûr sans quitter le fil Java ou réécrire l'appelant (ADR-069) | M4 |
| T-205 | vérification dynamique des accès : surveiller les écritures réelles | M4, avec la validation (C-24) |
| T-222 | réduction flottante déterministe : demande le moteur parallèle | M4 |
| T-223 | 32 exécutions comparées identiques : demande C-21 et C-25 | M4 |
| T-381 | mémoïsation interdite si non pure : aucun `result_cache` avant le code déporté | M4 |
| T-384 | démarrage à chaud mesuré : demande deux vraies parties avec des unités chaudes | partie de Killian |
| étalonnage A/A en jeu | aucune unité chronométrée sur un serveur au repos | partie chargée de Killian |
| quarantaines (R-551) | aucun incident lié à une unité avant le déport et la validation | M4 |

T-382 n'est pas une réserve : le contrôle par entrée de `workload.db` a été écarté
volontairement au profit du « tout ou rien » (ADR-048, décision de Killian du
2026-11-05).

Les réserves héritées de M2 restent ouvertes : T-190, T-194, T-262, T-267, T-212
(ADR-065). S'y ajoutent, hors DoD : la précision de C-11 sur les appels par interface et
sur les éléments de tableau ; `rfx.compat.quarantines`,
`rfx.compat.conflicting_transformers` et `rfx.cache.*`, qui attendent leur producteur.

## Conséquences

- M4 (Exécution sûre : snapshots, command buffers, commit, validation) commence par la
  lecture des fiches de C-19 à C-26 et de leurs IF, DM et INV, avant tout code.
- M4 contient la **première transformation réelle du jeu**. Elle ne se fera qu'avec
  l'accord explicite de Killian, donné pour elle.
- Les réserves ne sont pas oubliées : chacune garde sa case ouverte.
