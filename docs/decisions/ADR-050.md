# ADR-050 — Graphe d'appel (C-07) : lecteur de bytecode maison, résolution prudente

- **Date** : 2026-10-17
- **Statut** : accepté pour le cœur ; corrigé par l'ADR-051 (un appel par une interface
  n'est jamais résolu) ; le branchement en jeu reste à faire
- **Composants** : C-07 (Call Graph) ; crates `rfx-bytecode` et `rfx-analyzer`
  (PARTIE 3)
- **Exigences** : PARTIE 5.7, R-340, R-341, P-02, FM-15, PARTIE 19.2 (entrées non
  fiables), T-160 à T-164, INV-13
- **Demande** : Killian, 2026-10-17, « go la suite » ; C-07 choisi parce que C-10
  s'appuie sur son graphe et que C-08 orchestre les analyses

## Contexte

C-07 construit, pour une unité de travail, le graphe des méthodes qu'elle peut
appeler. La spec le place en Rust (`rfx-analyzer`), avec un lecteur de bytecode à part
(`rfx-bytecode`). Son acceptance exige « zéro faux résolu » : aucune arête ne doit
être déclarée résolue alors qu'elle ne l'est pas.

## Décision

1. **Un lecteur de `.class` maison, sans dépendance.** Le format (JVMS §4) est stable
   et borné, et une bibliothèque tierce serait une dépendance lourde de plus, ce qui
   n'est pas du ressort de l'assistant. Seul ce que l'analyse utilise est lu :
   - le réservoir de constantes complet (17 étiquettes, `Long` et `Double` sur deux
     emplacements, UTF-8 modifié) ;
   - la hiérarchie et les méthodes, avec leur attribut `Code` ;
   - `BootstrapMethods` ;
   - le parcours des instructions : `tableswitch` et `lookupswitch` avec leur
     alignement, préfixe `wide`.

   Les octets sont non fiables : toute incohérence rend une erreur, jamais une panic,
   et un compteur lu ne fait jamais réserver plus de mémoire que les octets restants.
   Une instruction inconnue fait refuser la méthode entière, car un site d'appel
   manqué ferait conclure à une méthode qui n'appelle rien.
2. **Résolution.** Une arête résolue désigne la méthode qui s'exécutera :
   - **liée statiquement** (`invokestatic`, `invokespecial`, méthode privée ou finale,
     classe finale) : résolue, même quand la classe est absente de l'index. Le nœud est
     alors externe et n'est pas exploré. FM-15 vise les appels dont la résolution exige
     la hiérarchie, c'est-à-dire les appels virtuels ;
   - **virtuelle** : on prend les classes concrètes chargées qui descendent du
     propriétaire, puis la méthode que la JVM choisirait pour chacune (JVMS §5.4.6 :
     super-classes, puis méthodes par défaut). Une cible : monomorphe. Deux à quatre :
     polymorphe borné. Plus de quatre, aucune, ou une classe absente sur le chemin :
     non résolu (R-341, P-02) ;
   - **lambda** (`LambdaMetafactory`) : la méthode d'implémentation lue dans le
     réservoir. Une référence de méthode virtuelle (`REF_invokeVirtual`, comme
     `String::length`) repasse par la résolution virtuelle ;
   - **réflexion** (`Method.invoke`, `MethodHandle.invoke*`, `newInstance`) : non
     résolue, et signalée ; **autre `invokedynamic`** (concaténation) : non résolu.
3. **Prudence aux frontières de l'index.** Une sélection qui croise une classe absente
   sans avoir trouvé sa réponse est « inconnue », et l'appel non résolu. C'est vrai même
   quand la classe absente est une interface du JDK à côté d'une méthode par défaut
   connue : l'interface absente pourrait en fournir une plus spécifique. Seule
   exception : `java/lang/Object`, dont les méthodes sont fixées par le JDK et listées
   dans le code.
4. **Monde fermé.** « Monomorphe » vaut pour les classes chargées au moment du calcul.
   Charger une nouvelle sous-classe peut ajouter une cible : le graphe doit être
   recalculé quand l'index change. C-08 en portera la responsabilité (R-350).
5. **Constat sur le compilateur** : depuis Java 11 (JEP 181), `javac` appelle une
   méthode privée de la même classe par `invokevirtual`, et non par `invokespecial`
   (vérifié par `javap` sur les classes de test). Une méthode privée ne pouvant pas être
   redéfinie, l'appel est traité comme exact.
6. **Bornes** (R-340) : profondeur 12, 2 000 nœuds. La racine est à la profondeur 0 ;
   un nœud à la profondeur maximale qui a des appels n'est pas exploré, et le graphe est
   alors marqué `truncated`. La récursion est détectée par un Tarjan itératif, sans
   aucune pile d'appels exposée à la profondeur du graphe. Les arêtes observées à
   l'exécution se fusionnent sans doublon et comptent pour les cycles.
7. **Classes de test** compilées par `javac --release 17` depuis des sources écrites
   pour le projet (`rfx-bytecode/tests/fixtures`), versionnées compilées pour que les
   tests Rust n'aient pas besoin d'un JDK. Aucune classe tierce n'est redistribuée.
8. **Options non déclarées** : `analysis.max_call_depth` et
   `analysis.max_nodes_per_workload` restent des constantes tant que C-07 ne tourne pas
   en jeu (`CLAUDE.md` §6 : n'est déclarée qu'une option lue par du code qui tourne).

## Vérification

- `rfx-bytecode` : 12 tests.
  - Les 23 classes de test se lisent.
  - Les sites d'appel sont exacts et dans l'ordre ; leurs positions après deux
    `switch` décalés sont celles de `javap`.
  - Les `invokedynamic` portent leur méthode d'amorçage et leurs handles.
  - Robustesse : chaque troncature de chaque classe est une erreur, et 5 000
    altérations aléatoires ne provoquent aucune panic. L'UTF-8 modifié couvre le nul
    sur deux octets et les demi-codets.
- `rfx-analyzer` : 15 tests.
  - T-160 : appel monomorphe, statique, privé, final, constructeur, `super`.
  - Polymorphe borné (3 cibles) et non borné (5).
  - Méthode par défaut.
  - T-161 : lambda, référence statique, référence virtuelle.
  - T-162 : réflexion.
  - T-163 : récursion directe et mutuelle.
  - T-164 : profondeur et nombre de nœuds.
  - FM-15 : classe absente.
  - Arêtes observées, métriques.
  - Les trois cas « zéro faux résolu » : méthode héritée de `Thread`, interface du JDK
    voisine d'une méthode par défaut, référence `String::length`.
- **Défauts volontaires** : 7 sur le lecteur, 11 sur l'analyseur, tous détectés.
  - Trois avaient d'abord survécu, et chacun a révélé un trou dans les classes de test.
  - Le remplissage des `switch` tombait à zéro par coïncidence d'alignement.
  - L'interface du JDK voisine d'une méthode par défaut n'était pas couverte.
  - Le motif d'une mutation était faux ; corrigé, la mutation est tuée.

## Conséquences

- Restent à faire : le branchement (faire parvenir à `rfx-core` les octets des classes
  sondées par C-04, construire les graphes hors tick, publier `rfx.callgraph.*`),
  puis l'acceptance (200 méthodes de référence, plus de 80 % résolues, zéro faux
  résolu). Le corpus de référence ne pourra pas être fait de classes de Minecraft ou de
  mods, qu'on ne redistribue pas : il sera lu sur l'installation locale, ou fait des
  classes du mod lui-même.
- Le taux de résolution dépendra fortement de ce que contient l'index : sans les
  classes du JDK, tout appel virtuel vers le JDK est non résolu. C'est prudent, et
  c'est ce que l'acceptance mesurera.
