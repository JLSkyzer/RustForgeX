- **Jalon** : M4 (Exécution sûre)
- **Composants** : C-19, C-21, C-22, C-23, C-24, C-25, C-26
- **Exigences** : PARTIE 5.19 à 5.26, PARTIE 30 (M4), DM-16, SM-03, SM-04, SM-05,

- **Demande** : Killian, 2026-11-05, « ok go fait ce que ta a faire et après tu revient

## Contexte

La PARTIE 30 attend de M4 « offload réel des workloads purs vers les workers Rust,
snapshot, command buffer, commit ordonné, validation, rollback », avec pour sortie « premier
`RUST_OFFLOAD` validé en production, gain mesuré ». La DoD compte T-280..T-284,
T-300..T-302, T-310..T-316, T-320..T-323, T-330..T-334, T-340..T-342, T-350..T-353 et
T-600..T-615.

## Ce que le cahier ne dit pas

**Quel code Rust exécute un `RUST_OFFLOAD` ?** Un workload est une méthode Java. Le
cahier offre trois sources de code natif, et aucune n'existe en M4 :

- la traduction du bytecode en RF-IR puis sa compilation (C-28 à C-30) : M6 et M7, et
  c'est `RustTransformed` (TL5), pas `RustOffload` ;
- une implémentation native fournie par le SDK ou par RF-X : `RustNative` (TL6), SDK en
  M8 ;
- « offload d'opération sans transformation » (PARTIE 10.1, `<= TL4`) : la seule piste
  de TL4, mais le cahier ne dit pas quelles opérations ni comment elles sont reconnues.

Exécuter le code **Java** sur les workers est impossible tel quel : ce sont des fils
natifs, non rattachés à la JVM, et les rattacher ferait de l'offload un `JavaParallel`
(TL3), qui garde le coût de la JVM.

## Décision

1. **L'ordre des travaux** suit la dépendance, du plus pur au plus proche du jeu, et
   rien ne touche au jeu avant la question 1 :
   1. **C-21 Command Buffer** et **C-23 Conflict Detection**, dans un nouveau crate
      `rfx-exec` (arborescence de la PARTIE 3) : purs, testables hors jeu ;
   2. **C-24 Validation** (SM-03, oracle de comparaison) et **C-26 Rollback**
      (révocation, bannissement), dans `rfx-validate` : purs ;
   3. **C-22 Commit Engine**, côté Rust (collecte, tri, validation, budget) puis côté
      Java (applicateurs) ;
   4. **C-19 Snapshot** et **C-25 Shadow Execution**, qui lisent le jeu.
2. **DM-16 (`Command`)** est défini pour la première fois dans `rfx-model`. Les types
   que le cahier nomme sans les décrire (`EntityPatch`, `PacketTarget`, `BlobRef`...)
   reçoivent la forme la plus simple qui les rende applicables et comparables ; un
   buffer ne se persiste pas, une correction ultérieure ne demande donc aucune
   migration de fichier.
3. **La première transformation réelle du jeu** (application d'un buffer par C-22) ne
   sera faite qu'avec l'accord explicite de Killian, donné pour elle (ADR-072).

## Avancement : C-21 et C-23 (2026-11-05)

Faits dans `rfx-exec`, sans rien toucher au jeu, avec DM-16 dans `rfx-model` :

- **C-21** : buffer append-only puis scellé (R-460), clé d'ordre `(priorité, clé stable,
  rang)` puis départage par workload puis par tâche (R-461), borne de 4 096 commandes
  dont le dépassement jette le buffer entier (R-462), régions lues enregistrées (R-463),
  transitions de SM-05 en avant seulement, un buffer appliqué ne se jette plus (R-511).
  T-300, T-301 (1 000 ordres d'arrivée), T-302.
- **C-23** : epochs par région, par domaine et « tout » ; péremption (R-441) et conflit
  dans le tick, le premier en ordre gagne ; plafond de vérifications, dont le
  dépassement rejette (R-481). T-320, T-321, T-323, et T-322 sur 10 000 cas synthétiques
  contre un oracle écrit à part : aucun faux négatif, aucun faux positif.
- 10 défauts volontaires, 10 détectés, dont le départage par workload, d'abord
  survivant faute de cas : les numéros de tâche suivent l'ordre de soumission, le
  workload non.

Choix de forme, sans effet sur la sûreté :

- **régions lues en plus du read set** : le `read_set` de la PARTIE 5.21 est un
  `AccessSet` par domaine ; la péremption de R-441 se juge par région. Le buffer garde
  les deux ;
- **granularité** : un bloc est versionné par son chunk, une entité par elle-même, le
  reste par domaine entier. Une **apparition d'entité** écrit tout le domaine des
  entités : elle change l'ensemble que d'autres ont pu parcourir (R-480). Un rappel
  Java ou une commande du SDK écrit `Any` ;
- **listes plutôt que bitsets** (R-481) : le coût reste borné par le plafond de
  vérifications, compté à chaque buffer ; un index par bitsets viendra si une mesure le
  demande.

En passant, un défaut de M3 corrigé : le test statique de T-392 ne lisait pas
`reasons.rs` (C-43) ni `experiment.rs`. Il les lit, et un test équivalent (T-245)
couvre `rfx-exec`. Chacun échoue si un nom de mod est glissé dans le code.

## Décision de Killian (2026-11-05)

Option D, recommandée (« Oui on part sur D ») : tout le socle d'abord, sans rien
activer — C-24, C-26, C-22 côté Rust, C-19, C-25. Le choix entre des noyaux natifs
pour des opérations reconnues (A) et l'avance de l'IR (B) se fera sur une mesure
d'une partie chargée : quelles unités chaudes sont pures, et ce qu'elles coûtent.
Écartées : C (`JavaParallel` d'abord, qui n'est pas du Rust et ne vaut que pour des
méthodes pures aux arguments simples).

## Avancement : C-22 côté Rust (2026-11-05)

`rfx_exec::commit` suit le protocole normatif de la PARTIE 5.22 : collecte des buffers
scellés, tri total, validation par C-23, application atomique par buffer, publication
des epochs. Choix :

- chaque commande est **vérifiée avant** la détection de conflits (chunk chargé, R-471 ;
  commande valide ; R-473) : un buffer invalide ne doit pas compter comme écrivain pour
  les suivants ;
- le budget de 2 ms est lu sur une horloge fournie par l'appelant ; un buffer hors
  budget est **rejeté**, jamais reporté (R-470) ;
- un échec d'application fait défaire, à rebours, les commandes déjà appliquées ; si
  l'une ne sait pas être défaite, l'issue est `Fatal` (FM-30, `E-2601`) ;
- l'application passe par un trait `Applicator` : dans les tests, un monde factice ;
  en jeu, des applicateurs Java, qui feront la première transformation réelle et
  attendent l'accord de Killian.

T-310, T-311, T-312, T-313, T-314, T-315 ; 9 défauts volontaires, 9 détectés. T-316
(sauvegarde identique avec et sans RF-X) demande le jeu.
