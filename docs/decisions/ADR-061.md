# ADR-061 — L'ordonnanceur démarré par le runtime, la base des unités de travail sur ses workers

- **Date** : 2026-10-29
- **Statut** : acceptée
- **Composants** : C-17 (Scheduler), C-09 et C-48 (base et persistance) ; C-18
- **Exigences** : PARTIE 5.17 (5.17.4, 5.17.5, R-420, R-421, R-423, FM-25), PARTIE 5.9
  (R-361), PARTIE 5.46 (R-690, R-692) ; livrable de M2 ; ADR-044 à ADR-049
- **Demande** : Killian, 2026-10-29 : « Base de données » — démarrer l'ordonnanceur avec
  le runtime, y passer le décodage parallèle et l'écriture de `workload.db` en tâches
  `BACKGROUND`, lui transmettre le relevé de charge ; l'analyse reste pilotée par Java.

## Contexte

Le livrable de M2 est un ordonnanceur « opérationnel, utilisé uniquement pour des tâches
internes (analyse, persistance) ». La crate `rfx-scheduler` est complète et testée, mais
`rfx-core` ne la démarre pas. Le relevé de charge que Java envoie chaque seconde est
rangé dans le statut, sans effet. La base vit sur un fil dédié (`RFX-IO`). Son décodage
parallèle du démarrage crée des fils à la volée (`RFX-DB-Load`).

Trois contraintes guident la conception :

- **Ordre.** La base a un seul détenteur, et ses demandes (lots, rotation, attente) sont
  servies dans l'ordre. Un pool à vol de travail ne garantit aucun ordre.
- **Jamais en ligne sous le verrou.** En série (`FORCE_SERIAL`, ou sur-souscription
  persistante, FM-25), `Scheduler::submit` exécute la tâche sur le fil qui soumet. Les
  lots sont confiés par le fil `rustforgex-db` **sous le verrou du runtime** : une
  écriture disque exécutée là ferait attendre le tick (R-690).
- **Pas d'interblocage.** Avec un seul worker actif, une tâche qui attend des
  sous-tâches en bloquant son fil ne les verrait jamais s'exécuter.

## Décision

1. **Soumission détachée** : `Scheduler::submit_detached`, qui refuse
   (`Backpressure`) au lieu d'exécuter en ligne quand l'ordonnanceur est en série. Le
   refus en contre-pression (`E-2401`) est inchangé.
2. **Exécuteur abstrait dans `rfx-cache`** : `Executor` (lancer un travail, ou le rendre
   s'il est refusé — jamais l'exécuter sur le fil appelant) et `Fork` (sous-travaux et
   attente). `rfx-cache` ne dépend pas de `rfx-scheduler`. Deux réalisations :
   - dans `rfx-core`, l'ordonnanceur. Le travail est une tâche `BACKGROUND` soumise en
     détaché ; ses sous-travaux sont des sous-tâches (`TaskContext::spawn`/`join`, qui
     exécute du travail en attendant) ;
   - dans `rfx-cache`, un fil dédié (`RFX-IO`) : le secours quand l'ordonnanceur n'a
     pas démarré, et l'exécuteur des tests. Ses sous-travaux s'exécutent à la suite.
3. **Exécution en série sur le pool** : la base garde un seul détenteur. Les demandes
   attendent dans une file bornée (`QUEUE_CAPACITY`, inchangée). Une seule tâche de
   vidage est en cours à la fois : elle sert la file dans l'ordre, puis se retire. Une
   demande arrivée pendant ce retrait relance une tâche. La première tâche relit
   d'abord le fichier. Une soumission refusée laisse la demande en file : la prochaine
   demande, ou la fermeture, relance le vidage.
4. **Fermeture** : elle se fait hors du verrou du runtime. On attend le vidage jusqu'au
   délai ; si aucune tâche n'a pu être lancée, ce qui reste est vidé sur le fil qui
   ferme. L'ordonnanceur s'arrête **après** la base.
5. **Décodage parallèle** : les tranches du fichier sont des sous-travaux du travail de
   relecture, sur des données partagées (`Arc`), sans fil créé à la volée.
6. **Démarrage** avec le runtime, au dimensionnement de la PARTIE 5.17.2
   (`SchedulerConfig::for_machine`). S'il échoue, le runtime continue avec le fil de
   secours, et le journal le dit. Les workers dorment quand il n'y a rien à faire.
7. **Relevé de charge** transmis à `Scheduler::report_external_load` (R-421) ; la
   fenêtre critique (R-423) est ouverte du début à la fin de chaque tick.

## Conséquences

- Plus de fils `RFX-IO` ni `RFX-DB-Load` en temps normal. Les workers (`rfx-worker-N`)
  sont des fils natifs jamais rattachés à la JVM : le capteur de charge, qui énumère les
  fils de la JVM, ne les compte pas, et l'ordonnanceur ne se prend pas lui-même pour
  une charge externe.
- Une base dont le vidage est refusé (série persistante) n'est plus écrite avant la
  fermeture, qui écrit alors sur son propre fil : rien n'est perdu, l'écriture est
  retardée.
- Vérifié en jeu (`runGameTestServer`, 2026-10-29) : 14 workers démarrés sur la machine
  de développement, `workload.db` relue par le pool (442 unités), aucun refus ni panique.
- Non couvert par un test : la relance d'une tâche quand une demande arrive pendant que
  la précédente se retire. La fenêtre est trop étroite pour un test déterministe, et
  l'attente de `flush` relance de toute façon le vidage toutes les 10 ms. Sans cette
  relance, un lot attendrait la demande suivante ; la fermeture le servirait, rien ne
  serait perdu.
- L'analyse reste sur le fil Java `rustforgex-analysis` : la passer sur l'ordonnanceur
  demanderait un pas d'analyse asynchrone (option écartée par Killian ce jour).
