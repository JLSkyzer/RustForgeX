# ADR-071 — T-204 : corpus annoté de 150 méthodes pour C-11, règles fixées avant la mesure

- **Date** : 2026-11-05
- **Statut** : acceptée
- **Composants** : C-11 (Data Flow Analyzer)
- **Exigences** : PARTIE 5.11 (acceptance), R-380, R-381, T-204 ; ADR-055, ADR-056
- **Demande** : Killian, 2026-11-05, « ok go », dans M3 (ADR-065)

## Contexte

L'acceptance de C-11 exige « zéro sous-approximation d'écriture sur le corpus annoté
de 150 méthodes ; au moins 60 % des méthodes du corpus classées avec
`precision = EXACT` ». Le cahier ne fournit pas ce corpus. Le construire soi-même
expose à un biais : choisir des méthodes que l'analyse sait déjà traiter. Ce document
fixe donc le corpus et ses règles **avant** la première mesure ; il ne sera modifié
ensuite que pour corriger une annotation fausse, chaque correction étant consignée
ci-dessous.

## Décision

1. **Le corpus** (`rfx-bytecode/tests/fixtures/src/corpus`, écrit pour ce projet) :
   150 méthodes en sept familles, de taille fixée d'avance :

   | famille | méthodes | contenu |
   |---|---|---|
   | `Pure` | 25 | calculs, boucles, `switch`, tableaux et objets locaux, concaténation, exception attrapée sur place |
   | `ModState` | 25 | statiques du mod, objets du mod reçus ou tenus dans un statique, receveur partagé |
   | `Game` | 25 | état du jeu par les classes d'ancrage : entité, inventaire, block entity, niveau |
   | `Arrays` | 20 | tableaux de statiques, de paramètres, d'objets du jeu ; alias ; tableaux locaux publiés |
   | `Calls` | 25 | aides, constructeurs, fabriques, récursion directe et mutuelle, chaîne de quatre appels, échappement par un appelé |
   | `Poly` | 15 | classe abstraite à trois implémentations, redéfinition, interface, méthode par défaut, `super` |
   | `Hard` | 15 | lambdas, référence de méthode, réflexion, collections et méthodes du JDK, natif, verrous, exception propagée |

   Les classes d'ancrage (`net/minecraft/...`) sont des bouchons de quelques lignes
   écrits ici : seul leur nom compte pour la table des domaines. Rien de Minecraft
   n'est repris.
2. **La vérité** est annotée sur chaque méthode (`@W.EntityState`, `@W.ModStatics`,
   `@W.Unknown`, `@W.Nothing`...). Elle se déduit de la mémoire **réellement** écrite à
   l'exécution, hors des objets que la méthode a créés et qui ne lui ont pas échappé
   avant l'écriture, par les règles de la PARTIE 5.11 : champ d'un objet → domaine de sa
   classe (sans ancre : `Unknown`) ; statique → `ModStatics` (`JavaStatics` pour le JDK) ;
   élément de tableau → domaine de l'objet ou du statique d'où vient le tableau. Pour un
   appel virtuel, la vérité est l'union sur les implémentations du corpus.
3. **Sous-approximation** : une méthode est sous-approximée si un domaine de sa vérité
   manque à l'ensemble d'écritures calculé, alors que cet ensemble n'est ni de précision
   `UNKNOWN` ni porteur du domaine `Unknown`. Ces deux formes couvrent tout : C-10 les
   tient pour en conflit avec tout (`dependency.rs`, `unknown`). Les effets de bord
   inconnus (`side_effects.unknown`) ne couvrent **pas** les écritures : ils ne disent
   rien des domaines.
4. **EXACT** : une méthode compte comme `EXACT` si ses écritures portent
   `precision = EXACT` **et** valent exactement sa vérité. Un `EXACT` aux domaines faux
   est un défaut, compté à part et bloquant (« faux EXACT »).
5. **Le JDK n'est pas dans l'index du test**, comme pour les autres tests de C-11 : ses
   classes ne sont pas redistribuées. Un appel vers le JDK (sauf `Object.<init>`) est
   donc un appel sans code, inconnu. En jeu, la hiérarchie contient le JDK ; le ratio
   mesuré ici ne transpose pas à une partie, que mesure `rfx.dataflow.exact_ratio`.
6. **Le test** (`rfx-analyzer/tests/corpus.rs`) échoue sur toute sous-approximation, tout
   faux `EXACT`, toute méthode non annotée d'une classe du corpus, un total différent de
   150, et un ratio `EXACT` sous 60 %. Il imprime le détail par famille.

## Résultats (première mesure, 2026-11-05, corpus non retouché)

| famille | méthodes | `EXACT` | sous-approximées | faux `EXACT` |
|---|---|---|---|---|
| `Pure` | 25 | 23 | 0 | 0 |
| `ModState` | 25 | 10 | 0 | 0 |
| `Game` | 25 | 23 | 0 | 0 |
| `Arrays` | 20 | 7 | 0 | 0 |
| `Calls` | 25 | 18 | 0 | 0 |
| `Poly` | 15 | 12 | 0 | 0 |
| `Hard` | 15 | 2 | 0 | 0 |
| **total** | **150** | **95 (63,3 %)** | **0** | **0** |

Acceptance tenue : zéro sous-approximation, 63,3 % `EXACT` (cible 60 %). Aucun des 95
`EXACT` ne repose sur un objet sans ancre : le test les compte à part, pour que le ratio
ne soit pas gonflé sans le dire.

Les 55 méthodes non exactes sont toutes de précision `UNKNOWN`, donc sûres. Ce qu'elles
montrent :

- **objets sans ancre** (objets du mod reçus ou tenus dans un statique, receveur
  partagé) : rendus `Unknown`, c'est la règle (ADR-055) ;
- **éléments de tableau** : toujours `Unknown`, y compris pour un tableau tenu dans un
  statique ou dans un inventaire, où la PARTIE 5.11 attend le domaine de la source du
  tableau (`ModStatics`, `EntityInventory`). C'est la principale perte de précision
  mesurée ici : 12 méthodes. Sûr, mais imprécis ;
- **appels par interface** (`viaInterface`, `viaDefault`) et **JDK absent de l'index**
  (lambdas, collections, `Math`, `String.valueOf`, exceptions construites) : inconnus,
  comme attendu (décision 5).

Défauts volontaires : trois sur l'analyseur (champ sans ancre lu comme vide, élément de
tableau lu comme vide, statique du mod lu comme statique du JDK), tous détectés par ce
test. Deux survivants, **équivalents** : l'ajout explicite de `Unknown` aux écritures
d'une racine inconnue, et la valeur par défaut des écritures d'un paramètre d'appelée
inconnue. Le premier double la composition, qui rend déjà `Unknown` tout site sans
résumé, y compris ceux d'un graphe tronqué ; le second ne sert que si l'arité d'un
résumé diffère de celle de son descripteur, ce que la construction des résumés exclut.
Un test de graphe tronqué a été ajouté pour garder le comportement observable,
quelle que soit la ligne qui l'assure.
