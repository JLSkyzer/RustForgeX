# ADR-049 — La base des unités de travail branchée dans le runtime

- **Date** : 2026-10-17
- **Statut** : accepté
- **Composants** : C-09 (Workload Database), C-48 (Persistence Store), C-27 (Runtime
  Core), C-05 (Profiler), C-41 (Mod Discovery)
- **Exigences** : R-360 à R-362, R-361, R-533, R-660, R-690 à R-692, R-700, DM-05,
  PARTIE 4.18, PARTIE 28 (`[cache]`)
- **Demande** : Killian, 2026-10-16, « branche la base dans rfx-core »

## Contexte

L'ADR-048 a livré `rfx-cache` sans appelant. Trois contraintes du runtime existant
décident de la forme du branchement :

1. **Un seul verrou.** Tout appel FFI passe par `runtime::with`, sous le mutex du
   registre que le tick partage. Copier la base entière sous ce verrou (environ 28 ms
   pour 20 000 unités, mesuré pendant l'ADR-048) ferait attendre le tick.
2. **Le descripteur était jeté.** `rfx_workload_register` calculait le `WorkId`, puis
   oubliait le descripteur ; la base en a besoin.
3. **L'environnement est côté Java.** Versions de Minecraft, Forge et Java, inventaire
   des mods : Java les connaît, Rust non. Le natif ne reçoit aucun chemin.

## Décision

1. **La base vit sur le fil `RFX-IO`** (`rfx_cache::DbService`, qui remplace le
   `PersistenceWriter` de l'ADR-048). Il relit le fichier à son démarrage, sans que le
   jeu attende, puis applique des lots : nouvelles unités (`observe`, filtre par entrée
   de R-360) et nouvelles dynamiques. Un changement de classe de coût entre à
   l'historique. Le fichier n'est réécrit que si la base a changé. Après un échec
   d'écriture, les lots restent appliqués en mémoire et le disque n'est plus sollicité
   (R-692). Une file pleine rend le lot intact à l'appelant.
2. **Le runtime n'envoie que des deltas, collectés par tranches.** `DbLink`
   (`rfx-core/src/db.rs`) garde les descripteurs enregistrés depuis le lot précédent
   et parcourt le profileur par tranches de 512 entrées, en ne retenant que les
   dynamiques vues depuis le début du cycle précédent. `rfx_db_sync` fait une tranche
   par appel ; le verrou est rendu entre deux appels, et le fil Java s'efface une
   milliseconde. Le tick n'attend donc jamais plus d'une tranche, quelle que soit la
   taille de la base. `WorkloadDynamics` est `Copy` : une tranche ne fait aucune
   allocation par élément.
3. **Java ouvre la base quand l'inventaire des mods est connu.** `RfxRuntime.discoverMods`
   (au chargement complet) démarre le fil `rustforgex-db` (`WorkloadDbLink`). Ce fil
   calcule `modid@version@début du sha256 du jar` pour chaque mod, hachage des jars
   compris, ce qui prend du temps, puis appelle `rfx_db_open` avec un blob `DbOpen`. Il
   synchronise ensuite toutes les cinq minutes. Les unités enregistrées avant
   l'ouverture attendent côté natif, au plus `profiler.max_workloads`. Le préfixe
   `rustforgex-` exclut le fil du relevé de charge (ADR-046).
4. **Empreinte d'environnement** (DM-05), calculée côté natif. Les chaînes venues de
   Java sont hachées par xxh3, et les mods triés avant hachage. S'y ajoutent la classe
   de matériel (`HardwareClass::class_hash`), la version du paquet natif et la
   **configuration entière**. Changer n'importe quelle option invalide la base : c'est
   plus prudent que de deviner lesquelles comptent (UNKNOWN = CONSERVATIVE). Les champs
   propres à une unité (`owner_mod_hash`, `bytecode_hash`, `deps_bytecode_hash`)
   restent nuls, car rien ne les calcule encore. Mettre à jour un mod change sa version
   et invalide donc la base entière, ce qui est prudent.
5. **L'arrêt ferme la base hors du verrou.** `runtime::shutdown` retire le runtime du
   registre, rend le verrou, puis confie un dernier lot complet et attend son écriture,
   au plus 10 s. `DbService::close` laisse le fil à lui-même au-delà du délai : l'arrêt
   du jeu n'attend jamais un disque qui ne répond plus. Il n'y a donc pas d'entrée FFI
   de fermeture.
6. **Mémoire.** La base est bornée par `cache.max_memory_mb` (défaut 128, PARTIE 28),
   et par ce que `memory.max_native_mb` laisse libre. Elle est comptée dans le budget
   natif (`Pool::Cache`, R-533), et le plafond suit le budget à chaque tranche. Ses
   entrées sont bornées par `profiler.max_workloads`, le `max_workloads` de R-362.
7. **Options déclarées** : `cache.enabled` et `cache.max_memory_mb`, seules lues par du
   code. `cache.max_disk_mb` n'est pas déclarée : `workload.db` est le seul fichier du
   cache, et sa taille suit la mémoire, 25 Mio sur disque pour 46,6 Mio en mémoire
   (ADR-048).
8. **Télémétrie** `rfx.db.*` (BENCHMARKS.md). Rien n'est publié avant l'ouverture,
   sauf les échecs d'ouverture (R-660). L'arrêt journalise un résumé : unités, issue de
   la relecture, écritures. Un fichier illisible relève de `E-3003` : il est mis de côté
   puis recréé.
9. **Nouvelles entrées FFI** : `rfx_db_open(handle, cbor, len)` et
   `rfx_db_sync(handle, *out_done)`, avec leurs équivalents JNI `dbOpen` et `dbSync`. Ce
   sont des ajouts : aucune entrée existante ne change de contrat.
   `rfx_workload_register` garde sa signature ; seul `Runtime::register_workload`,
   interne, reçoit désormais le descripteur.

## Vérification

- **Rust** :
  - 15 tests d'intégration du service (`rfx-cache/tests/persistence.rs`) : relecture en
    arrière-plan avec un lot confié pendant, dynamiques gardées puis mises à jour avec
    historique, remplacement d'une unité au code changé, plafonds d'entrées et
    d'octets, T-184, T-500 (relecture comprise), T-502 (base continuée en mémoire, plus
    aucune écriture tentée), etc. ;
  - `rfx-core` : l'empreinte suit chaque entrée sauf l'ordre des mods, l'attente est
    bornée, le plafond respecte le budget natif. Un test de bout en bout fait tourner
    40 ticks avec de vrais enregistrements de sonde, synchronise, ferme, relit le
    fichier, et y trouve 160 appels et `last_seen_tick = 40` ;
  - `rfx-ffi` : survie à un redémarrage (une unité enregistrée après le dernier lot
    n'arrive au fichier que par la fermeture à l'arrêt), parcours en trois tranches
    pour 1 200 unités, base désactivée, refus d'un handle invalide.
- **Java** : 6 tests de `WorkloadDbLink` (blob décodé, refus du natif, cycle par
  tranches, arrêt sur erreur, tous les appels sur `rustforgex-db`) ; télémétrie
  silencieuse avant l'ouverture ; catalogue R-562 complété.
- **Défauts volontaires** : douze, tous détectés. Le seul qui avait d'abord survécu,
  la fermeture retirée de l'arrêt, a révélé un test qui affirmait « écrite à l'arrêt »
  alors que le fichier venait de la synchronisation précédente. Le test a été
  corrigé.
- **En jeu** (`./gradlew runGameTestServer`, deux lancements, le 2026-10-17) :
  - premier lancement : base ouverte (3 mods), « aucun fichier au lancement »,
    `workload.db` écrit à l'arrêt (390 478 octets) ;
  - second lancement : « 413 unités relues au lancement » ;
  - aucun avertissement ni erreur du mod dans `debug.log`. Le serveur de test s'arrête
    après un seul tick observé : les mesures du profileur y sont donc nulles, d'où le
    test de bout en bout ci-dessus.

## Conséquences

- La relecture n'alimente encore aucune décision : la base retient ce qui a été
  observé, et le moteur de décision (M3) en sera le lecteur.
- Une partie plus courte que cinq minutes n'écrit qu'à l'arrêt ; un plantage avant le
  premier cycle perd ce qui a été découvert depuis le lancement.
- Les dynamiques d'un lancement remplacent celles du précédent pour une même unité :
  le profileur repart de zéro à chaque lancement, et la base garde la dernière
  observation, pas une moyenne de plusieurs parties.
